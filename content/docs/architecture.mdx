The browser never speaks to Redis or to the encoder. It sends a file to `cmd/api`. The API writes the bytes to object storage, records the upload in PostgreSQL, and publishes one message per job to a Redis stream. `cmd/worker` is a separate binary running its own event loop — it reads those messages, fetches the source from storage, runs FFmpeg, and writes results back to Postgres.

PostgreSQL is the authoritative record of what happened. Redis is the delivery mechanism. If the stream is flushed, the job rows remain in Postgres — the worker never invents work the database didn't authorize, because every message carries only a UUID that the worker loads from Postgres before doing anything.

## Upload lifecycle

The browser sends a multipart POST to `/api/v1/media` with `project_id`, `file`, and a JWT. The API checks that the project belongs to the authenticated user, then streams the file bytes to object storage under a key like `yellowbird/<uuid>-<sanitized-name><ext>`. Only after that upload succeeds does the API write the media row — if the database insert fails, the object is deleted to avoid orphans.

The media row starts at status `uploaded`. For a video MIME type, five jobs are created: thumbnail, preview, and H.264 transcodes at 360p, 720p, and 1080p. Any other file type gets thumbnail and preview only. Each job is a Postgres row plus an `XADD` of that row's UUID onto the stream `yellowbird:jobs`.

A worker in consumer group `yellowbird-workers` reads with `XREADGROUP`. Because sibling jobs for the same upload often run concurrently, `internal/worker/cache.go` keeps the source on local disk for 15 minutes, guarded by `singleflight` so concurrent goroutines share a single download. FFmpeg writes to a temp file. The worker uploads it, inserts a rendition row, and marks the job completed. `SyncStatus` then acquires a `SELECT FOR UPDATE` lock on the media row — when every sibling job is done, media becomes `ready`. One failed job moves media to `failed`, even if other renditions exist. The worker then calls `XACK`. Until that ack, the message stays in Redis's pending-entries list.

## Crash recovery

A recovery goroutine runs every 30 seconds. Any pending message idle for five minutes is claimed with `XCLAIM`. When the delivery count reaches three, the worker marks the job failed, runs `SyncStatus`, copies the message to `yellowbird:jobs:dlq`, and acknowledges the original. A job whose database status has already advanced past `queued` is acked and silently skipped.

The `SELECT FOR UPDATE` lock is what prevents two workers completing sibling jobs simultaneously from both attempting the same state transition on the parent media row. Processing is at-least-once — the duplicate-delivery guard handles jobs that arrive twice.

Worker goroutines are detached from the process shutdown signal with `context.WithoutCancel`. A `SIGTERM` does not abort an in-flight FFmpeg call; the process waits for all running goroutines before exiting.

## What isn't built

Several internal packages exist as package-level comments and nothing more: `internal/ws` (WebSockets), `internal/rl` (rate limiting), `internal/backpressure`, `internal/storagepolicy`, `internal/grpcserver`. Do not build a client against any of these — none are on the request path, and none produce responses. There is no HLS playlist in the worker; a video becomes JPEG, MP4 preview, and H.264 MP4s at the three target heights, and nothing else.
