title: Web workspace
description: The Next.js app — how it authenticates, uploads files with progress tracking, and polls for renditions.

The workspace is `yellowbird-web`, a Next.js app on React 19 served at `yellowbird.amaanworks.me`. It doesn't run FFmpeg, open a database connection, or talk to Redis. Every action — uploading a file, creating a project, deleting a rendition — is an HTTP request to the Go API.

`NEXT_PUBLIC_API_URL` controls which API origin the client uses. When unset, it defaults to `https://api.amaanworks.me`. There's no Next.js rewrite rule in the middle, so requests go cross-origin from the browser. The API's CORS allow-list covers `https://yellowbird.amaanworks.me` and localhost on ports 3000, 3001, and 5173. Any other origin is rejected with a 403 before the handler runs.

## Session

The workspace stores the login token as `yb_auth_token` in localStorage and the user JSON as `yb_auth_user`. Login writes both. Three things clear them: an explicit sign-out, a 401 response from any protected endpoint, or the client detecting that the token's `exp` has passed. There is no token refresh — tokens are valid for 24 hours.

Register posts `name`, `email`, and `password` but does not write a session on its own. Login posts `email` and `password`, and stores both values if the API returns a token.

## Pages

`AuthGate` wraps the workspace root (`/`) and the library (`/library`). If `yb_auth_token` is missing or expired, the component redirects to `/login?next=<path>`. Login and register are outside that gate.

The workspace at `/` is where you pick or create a project, drop a file, and watch encoding progress. During upload the player uses the local object URL — the file plays immediately without waiting for any processing to finish. Once renditions arrive, the player switches to the hosted URL. Labels read Poster, Preview, 360p, 720p, or 1080p depending on what's available.

`/library` lists all media for the current user. From there you can open an item in the workspace or delete individual renditions.

## Upload and polling

The file upload uses `XMLHttpRequest` rather than `fetch` so the page can receive progress events from `xhr.upload.onprogress`. The request goes to `POST /api/v1/media` with multipart fields `project_id` and `file`. All other API calls — project management, job status, rendition listing — use `fetch` with `Authorization: Bearer <token>`.

After the upload returns a media ID, the page enters a polling loop. It fetches the media row, the job list, and the rendition list together every 2.5 seconds for up to 15 minutes. The loop exits when:

- The media status is `ready`.
- No job is still `queued` or `running`, and at least one rendition exists — the page treats this as complete even if the media row hasn't caught up yet.
- Every job has failed, or the media status is `failed` with no renditions — in this case the page surfaces the job error.

On timeout, any renditions that did arrive are displayed. If none arrived, the error message reports that the worker is still processing.
